# MCP-доступ к «КЛИМАТ-ПРО»

Отдельный MCP-сервер даёт Claude, Codex и другим MCP-клиентам структурированный
доступ к данным сайта. Он работает от имени обычного пользователя Supabase:
`service_role`, произвольного SQL и обхода RLS здесь нет.

## Что доступно

MCP публикует пять инструментов:

- `kp_get_context` — пользователь, профиль, роли, сущности, действия и JSON Schema
  всех payload;
- `kp_query` — чтение проектов, задач, ТЗ, комментариев, клиентов, финансов,
  команды, файловых метаданных, заявок, активности и пользователей;
- `kp_prepare_change` — валидация и предпросмотр изменения;
- `kp_confirm_change` — выполнение предпросмотра по одноразовой точной фразе;
- `kp_cancel_change` — отмена предпросмотра.

Операции записи покрывают CRUD проектов, задач, клиентов и транзакций, платежи и доли проектов, версии ТЗ,
комментарии, участников проектов, заявки, сообщения, видимость/удаление файлов и
административное управление пользователями. Фактический доступ всегда ограничен
существующими RLS-политиками и RPC сайта.

Бинарная загрузка/скачивание файлов и операции, принимающие новый пароль, намеренно
не входят в JSON-инструменты первой версии. Для них нужен отдельный безопасный
resource/URL-elicitation поток.

## Локальный режим stdio

Требуется Node.js 20 или новее.

```powershell
cd "F:\Сайт\redesign-v2-fresh\mcp"
npm ci
npm run login
```

`login` принимает обычный email либо логин сайта без `@`; пароль вводится скрыто.
Сессия сохраняется в `mcp/.local/session.json`, который исключён из Git. Access и
refresh token никогда не печатаются. Не копируйте этот файл другим людям.

После входа подключите один из файлов из `examples/` к MCP-клиенту и перезапустите
клиент. Для ручного запуска:

```powershell
npm start
```

Конфигурация Supabase берётся из `KP_SUPABASE_URL` + `KP_SUPABASE_ANON_KEY` или из
`VITE_SUPABASE_URL` + `VITE_SUPABASE_KEY` родительского `.env.production`.
Любая переменная с `service_role` приводит к отказу запуска.

## Как LLM меняет данные

Прямого write-tool нет. Модель обязана выполнить два отдельных вызова:

1. `kp_prepare_change` с `action` и `payload`.
2. Показать пользователю `preview`, `confirmationToken` и `confirmation`.
3. Только после согласия вызвать `kp_confirm_change` с тем же токеном и точной
   фразой.

Токен живёт 5 минут, принадлежит одному пользователю и одноразовый. Перед записью
сервер повторно читает целевую запись; если она изменилась после preview, действие
отменяется.

Пример подготовки:

```json
{
  "action": "task.set_status",
  "payload": {
    "id": "00000000-0000-4000-8000-000000000000",
    "status": "Готово"
  }
}
```

Полный список значений и обязательных полей клиент получает из ресурса
`klimat://actions` или через `kp_get_context`.

## Streamable HTTP

Локальный HTTP запускается так:

```powershell
npm run start:http
```

По умолчанию endpoint — `http://127.0.0.1:8788/mcp`. Каждый POST обязан содержать:

```text
Authorization: Bearer <короткоживущий access JWT пользователя Supabase>
Content-Type: application/json
```

Параметры:

- `KP_HTTP_HOST`, `KP_HTTP_PORT`;
- `KP_ALLOWED_HOSTS` — точный CSV-список разрешённых Host;
- `KP_ALLOWED_ORIGINS` — точный CSV-список browser Origin;
- `KP_HTTP_BODY_LIMIT` — лимит тела, максимум 2 MB.

Публиковать endpoint напрямую в интернет нельзя. Для удалённого режима нужны
HTTPS reverse proxy, закрытый allowlist и способ выдачи/обновления пользовательского
JWT. Production-публикация выполняется отдельным owner-gated шагом.

## Проверка

```powershell
npm test
npm audit --audit-level=low
```

Тесты включают in-memory MCP client/server, реальный дочерний stdio-процесс,
локальный Streamable HTTP, allowlist/Bearer-гейты, схемы действий, RLS-gateway fake,
одноразовые подтверждения и stale-preview.
