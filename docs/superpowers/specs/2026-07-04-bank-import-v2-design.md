## 1. Контекст и проблема

Категоризация банковских выписок работает плохо (владелец: «работает очень плохо, разработка потерялась»). Текущий код в `src/App.jsx`:
- `CAT_RULES` (~4167) — хардкод-словарь мерчантов под личную историю; substring-матч; 0 тестов.
- `guessCategory(description, type)` (~4251) — итерирует словарь, `d.includes(k)`, первое совпадение.
- Парсеры `parseTinkoff/parseSber/parseAlfa/parseYandex` + `parsePdfYandex` (координатный, рабочий).

Подтверждённые слабости (сверено с кодом):
1. **`bankCategory` извлекается, но выбрасывается** — `parseTinkoff`/`parseYandex` кладут категорию в объект, но импорт (`~5504/5523`) зовёт `guessCategory` без неё.
2. **Substring-матч** — ложные срабатывания без границ слов («metro» ловит «METRO Cash&Carry»).
3. **Sber/Alfa — `bankCategory:""`** жёстко.
4. **0 тестов** — правки вслепую.
5. **Хрупкость к формату** — хардкод индексов колонок.
6. **Порядок правил неявен** — первое совпадение.
7. **Нет запоминания ручных переназначений.**

## 2. Постановка: что решаем, что отложено

Изначально владелец хотел **real-time канал** (операция в банке → сразу на сайт, без лишнего). Проверка выполнимости:
- Основной банк — **Яндекс Банк** (владелец — покупатель, не мерчант).
- API Яндекс Пэй `/orders/{id}` — только для мерчантов (входящие платежи от клиентов), к личным тратам доступа не даёт.
- Открытый банкинг РФ (стандарты ЦБ, методы для физлиц) — вступают в силу с 01.10.2026, Яндекс Банк как ПУ пока не подключён; не применимо сейчас.
- **Email и SMS на операции у владельца не приходят — только push в приложении.**

Вывод: настоящий real-time для физлица возможен только перехватом push (Android Notification Listener → вебхук) — хрупко, требует телефон онлайн, стороннее приложение с доступом ко всем уведомлениям. **Отложено** как отдельная итерация.

**Эта итерация = «умный импорт выписки v2»:** надёжный парсер PDF Яндекс Банка + классификация операций + обучаемый категоризатор + ручной review (владелец — финальный арбитр). Ядро (парсинг/классификация/категоризация) переиспользуется, если позже добавим push-канал.

## 3. Вводные (решения владельца при brainstorming)

- **Только Яндекс Банк** ведётся в дашборде (Сбер не учитывается → перевод Сбер→Яндекс себе НЕ является двойным учётом; это единственное появление денег на Яндексе, смысл назначает владелец вручную).
- **Ручной review — центр.** Владелец подтверждает/правит категории и назначения перед сохранением.
- **Переводы себе** (контрагент = сам владелец) — помечать, по умолчанию вне доход/расход статистики, возвращаемы одним кликом.
- **Персоналии в переводах физлицам** — сумму учитывать, ФИО/телефон вырезать (обезличивать).
- **Категоризация — цепочка слоёв с запоминанием** (не «идеальный парсер на всё»): система учится на правках владельца.
- **LLM — опциональный слой**, не в ядре (для переводов бесполезен — данных нет в PDF; для оплат помогает на незнакомых мерчантах). Локально на ПК владельца (приватность финансов), включаемый.

## 4. Архитектура

Три части, слабо связанные:

```
src/lib/bankParsers.js  — ЧИСТЫЕ функции (без React/сети), покрыты vitest:
  parseYandexPdf(rows)      → сырые операции {date, amount, sign, rawDesc}
  classifyOperation(op, me) → {type, counterparty, anonymized}
  normalizeMerchant(desc)   → merchant_key
  categorize(op, learned)   → {category, source}
  hashOperation(op)         → строковый ключ для дедупа
  dedupe(ops, existing)     → пометка повторов

UI: CsvImportModal (усиление существующего) — рендер review-таблицы,
    вызовы lib, сохранение подтверждённого + upsert правок в merchant_rules.

БД (Supabase): transactions (есть) + merchant_rules (новое) + настройка self_names.
```

Причины границ:
- Логика в `lib/` изолирована от UI/сети → тестируется юнитами на реальных (обезличенных) строках. Сейчас всё в монолите `App.jsx` без тестов.
- `merchant_rules` в БД (не localStorage) → переживает чистку кэша, синкается между ПК и ноутом.
- Review — тонкий слой над `lib`, не переписываем модалку с нуля.

## 5. Классификация операций (`classifyOperation`)

По описанию из PDF определяем тип:

| Тип | Признак | Обработка |
|---|---|---|
| `payment` | название мерчанта | категоризатор (§6) |
| `self_transfer` | контрагент ∈ «мои ФИО» | пометка, по умолчанию вне статистики, поле «назначение» для ручного смысла |
| `peer_transfer` | СБП физлицу (чужое ФИО + телефон) | сумму учитываем, ПДн вырезаем → «Перевод физлицу» |
| `technical` | капитализация %, кэшбэк, внутрибанковское | оставляем как обычную (владелец не отметил лишними), тип для группировки |

`me` — список «мои ФИО» (варианты написания). Без него `self_transfer` от `peer_transfer` не отличить. Начальное значение — из шапки выписки (владелец счёта), правится в настройке.

## 6. Категоризатор — цепочка слоёв (`categorize`)

Первый сработавший слой побеждает; в результат кладём `source` (для метки в review):

| # | Слой | source | Пример |
|---|---|---|---|
| 1 | Выученное (`merchant_rules`) | `learned` | прошлая правка «SUSHISHOP → Питание» |
| 2 | MCC из описания | `mcc` | `YANDEX*4121*` → 4121 → Такси |
| 3 | Словарь-затравка (частые), **границы слов** | `dict` | `magnit` ловит «MAGNIT MM», не «magnitola» |
| 4 | LLM (опция, выкл. по умолчанию) | `llm` | незнакомый бренд → подсказка, локально |
| 5 | Fallback | `none` | «Прочие расходы» + флаг «нужен выбор» |

Детали:
- **`normalizeMerchant`** перед слоями 1/3: «MAGNIT MM STANTSIONNYJ 12» → `magnit` (убрать номера/города/суффиксы). Разные точки сети = одно правило.
- **Границы слов** (regex `\b` / токенизация), не `includes()` — чинит слабость №2.
- **MCC-таблица** — стандартные группы MCC→категория; применяется, когда MCC присутствует в описании (формат `YANDEX*NNNN*`).
- **Слой 4 (LLM):** интерфейс `categorizeLLM(merchant) → category|null` заложить, реализацию отложить. Предполагаемое размещение — локальная модель (Ollama/llama.cpp) в WSL на ПК владельца (там же прод), дёргается edge-функцией; финансовые данные не уходят в облако.

## 7. Review-экран (усиление `CsvImportModal`)

Таблица операций, строка = операция:
`[дата] [сумма±] [тип-бейдж] [категория ▼] [мерчант/назначение + метка source] [✓ вкл]`

- Правка категории в селекте → при импорте `upsert` в `merchant_rules` (обучение).
- **Метка source** под мерчантом (`из словаря` / `MCC 4121` / `выучено` / `нужен выбор`) — владелец видит, чему доверять, что проверить.
- `self_transfer` — строка приглушена, чекбокс «учитывать» выключен, поле «назначение» (ЗП/клиент) для ручного смысла.
- `peer_transfer` — ПДн вырезаны (иконка замка).
- Незнакомый (`source=none`) — жёлтая пометка «нужен выбор», не теряется.
- Сводка сверху + счётчик на кнопке импорта считает только реально импортируемое (self_transfer исключён).

Мокап согласован с владельцем (нейтральная тема виджета; на сайте — premium-dark golden при реализации).

## 8. Хранение и дедуп

**`merchant_rules`** (Supabase):
- Поля: `merchant_key` (нормализованный, уникальный на владельца), `category`, `owner_id`, `updated_at`.
- RLS: только владелец (личные финансы).
- Читается в память при открытии импорта (слой 1 цепочки).

**Настройка «мои ФИО»** (`self_names`): массив вариантов написания владельца — в профиле или отдельной строке настроек. Seed из шапки выписки.

**Дедуп:** `hashOperation` = `дата + сумма + normalizeMerchant(описание)`. При импорте сверка с существующими `transactions` за период выписки → повтор помечается «уже есть», по умолчанию skip. Защита от двойного импорта пересекающихся выписок.

## 10. Scope и YAGNI

**В этой итерации:** `parseYandexPdf` (докрутка существующего) + `classifyOperation` + `categorize` (цепочка, слои 1-2-3-5 рабочие; слой 4 LLM — только интерфейс) + `dedupe` + review-UI + `merchant_rules` + `self_names`. Банк — только Яндекс.

**НЕ сейчас** (отдельные итерации; ядро переиспользуется):
- Real-time push-канал (Android Notification Listener → вебхук).
- LLM-слой [4] — только интерфейс-заглушка, реализация позже.
- Сбер/Альфа/Тинькофф — парсеры остаются рабочими, фокус доработки на Яндекс.

## 11. Риски и открытые вопросы

- **Формат PDF Яндекс Банка может меняться** — координатный парсер хрупок к смене вёрстки. Митигация: тесты на фикстурах ловят регресс; парсер терпим к отсутствию полей.
- **Определение «перевод себе»** зависит от совпадения ФИО — если банк пишет ФИО по-разному, возможны пропуски. Митигация: список вариантов «мои ФИО», ручная правка в review как страховка.
- **Нормализация мерчанта** — эвристика; агрессивная нормализация может слить разные мерчанты. Митигация: тесты на реальных примерах, консервативные правила.
- **Проверка на реальных данных** — владелец прогонит на свежей выписке после реализации (его слова: «надо тестить»).
