# MCP-доступ LLM к «КЛИМАТ-ПРО»

**Дата:** 2026-08-11
**Статус:** принят к реализации по прямому запросу владельца

## Цель

Дать Claude, Codex и другим MCP-совместимым LLM стандартный доступ к рабочим
данным «КЛИМАТ-ПРО»: модель должна понимать структуру системы, читать доступные
пользователю сущности и выполнять разрешённые изменения с обязательным preview и
отдельным подтверждением.

## Архитектура

В репозитории появляется отдельный Node.js-пакет `mcp/`. Он не входит во frontend
bundle и поддерживает два транспорта:

- `stdio` — основной локальный режим для Claude Desktop, Codex и других клиентов,
  запускающих MCP-процесс;
- Streamable HTTP — stateless endpoint для клиентов, умеющих подключаться по URL и
  передавать `Authorization: Bearer <Supabase access token>`.

MCP-сервер никогда не использует `service_role`. Каждый запрос выполняется через
Supabase-клиент конкретного пользователя, поэтому таблицы, RPC и Edge Functions
применяют те же RLS-политики, что и сайт.

## Инструменты

### `kp_get_context`

Возвращает текущего пользователя, профиль, роли, навигационную карту, доступные
сущности, действия и правила подтверждения.

### `kp_query`

Единый read-only инструмент для безопасного списка/деталей:

- `projects`, `tasks`, `tz_versions`;
- `project_comments`, `task_comments`, `client_messages`;
- `clients`, `transactions`;
- `project_files`, `project_members`, `project_payments`, `project_shares`;
- `project_requests`, `activity`, `users`.

Фильтры ограничены белым списком. Ответы ограничены по размеру. Произвольных
таблиц, колонок и SQL нет.

### `kp_prepare_change`

Валидирует одно действие, читает текущую запись через RLS и возвращает preview:
что изменится, что удалится, одноразовый `confirmationToken` и точную фразу
подтверждения. Внешнее состояние на этом шаге не меняется.

### `kp_confirm_change`

Выполняет ранее подготовленное действие только если:

- токен существует, не истёк и ещё не использован;
- подтверждение совпадает дословно;
- пользователь тот же;
- исходная запись не изменилась после preview.

Токен живёт только в памяти процесса 5 минут и после одной попытки уничтожается.

### `kp_cancel_change`

Удаляет подготовленное действие без изменений данных.

## Действия первой версии

- проекты: создать, изменить, удалить, взять, освободить, отозвать; атомарно заменить платежи и доли;
- задачи: создать, изменить, удалить, сменить статус;
- ТЗ: предложить версию, подтвердить, отклонить;
- комментарии проекта: добавить, решить/переоткрыть, удалить;
- комментарии задачи: добавить, решить/переоткрыть;
- клиенты: создать, изменить, удалить;
- операции финансов: создать, изменить, удалить;
- команда проекта: добавить, изменить роль, удалить;
- заявки заказчика: создать, принять, отклонить;
- переписка с заказчиком: отправить сообщение;
- файлы: изменить видимость заказчику, удалить;
- админ: изменить пользователя, набор ролей, удалить пользователя.

## Авторизация

### Локальный `stdio`

Команда `npm run login` в `mcp/` выполняет обычный Supabase password sign-in и
сохраняет только сессию в локальный gitignored-файл. MCP-сервер использует access
и refresh token этой сессии; Supabase самостоятельно обновляет JWT.

### Streamable HTTP

Каждый запрос обязан содержать короткоживущий Supabase access JWT. Сервер
проверяет его через GoTrue и использует тот же JWT для PostgREST/RPC. По умолчанию
HTTP слушает только `127.0.0.1`; публикация через reverse proxy является отдельным
owner-gated deploy-шагом.

## Безопасность

- RLS/RPC — единственный источник прав; собственная параллельная ролевая модель не
  создаётся.
- Нет `service_role`, raw SQL, произвольных таблиц и массовых wildcard-операций.
- Все мутации двухфазные и помечены MCP-аннотациями как write/destructive.
- Patch-поля фильтруются allowlist; `owner_id`, `author_id` и другие поля владения
  берутся из проверенной Supabase-сессии.
- Preview имеет fingerprint; stale preview не выполняется.
- Результат мутации не скрывает RLS-ошибку и не считает нулевое число изменённых
  строк успехом.
- Действия MCP best-effort маркируются в существующем `activity_log` без новой
  таблицы и без изменения живой БД.
- HTTP имеет лимит тела, host/origin allowlist и обязательный Bearer JWT.

## Границы первой версии

- Бинарная загрузка/скачивание файлов через MCP не входит в JSON CRUD-контур:
  для неё нужен отдельный resource/roots поток без base64 и без чтения
  произвольного пути на ПК.
- Создание пользователя и сброс пароля не принимают пароль через tool arguments;
  эти операции требуют URL elicitation/страницы сайта.
- Код, миграции и конфигурация готовятся в ветке. Merge в `main`, live DB и
  production deployment — только по отдельному адресному разрешению владельца.

## Критерии готовности

- MCP Inspector/SDK-клиент видит инструменты и ресурсы через stdio.
- Пользователь с валидной сессией получает только RLS-доступные данные.
- Read tool не меняет состояние.
- Любая мутация без prepare/точной фразы/актуального fingerprint отклоняется.
- Невалидные поля и неизвестные actions отклоняются до обращения к БД.
- Unit/integration tests покрывают каталог, авторизацию транспорта, подтверждения,
  stale preview и MCP tools/list + tools/call.
